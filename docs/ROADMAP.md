# Roadmap

## v0.9.1

- [ ] **Move `AppCoordinator` to `@Observable`.** `ObservableObject` publishes per object, so every view holding the coordinator re-renders whenever any property on it changes. That cost a dictation about 42% of a core on an M4 until the two values that change ten times a second were moved off it — the recording phase's level and elapsed time, and the microphone test level. Those are fixed, but the hazard is structural: the next rapidly-changing property put on this object does the same thing again, silently, and it does not look like the meter in a profile — it reads as SwiftUI layout. Observation gives per-property tracking, so a view is invalidated only by what it actually reads. Large: every view holding `runtime` is touched, and `AppRuntime`'s manual `objectWillChange` forwarding goes with it. **Measure a dictation before and after**, so the migration is judged on the thing it is for. ([Notion task](https://app.notion.com/p/3c3719370402812895e1faced1634f97))
- [ ] **Give setup's flow one piece of state instead of fourteen.** `OnboardingView` holds fourteen sibling `@State` properties and `prepare` clears them one by one. SwiftUI keeps a `Window` scene's `@State` alive after the window closes, so anything the list misses carries the previous run's answer into a Redo Setup — silently, with no symptom until someone redoes setup. That is not hypothetical: it is what made a redo open on the last page with a Done button that finished nothing. Gather the step-owned values into one struct with defaults so `prepare` becomes `flow = OnboardingFlow()` and adding a field cannot be half-done. `launchAtLogin` stays separate; it is seeded from `LaunchAtLoginService.state` rather than from a default. ([Notion task](https://app.notion.com/p/3c37193704028104a1dad44d1de257e5))
- [ ] **Stop the permissions step jumping when the microphone grant lands.** Granting swaps a one-line row for the picker, meter, status and help block, and the page is centred, so everything moves under the reader. It is the last height change left in setup — the shortcut alternatives and the key step's status row were both fixed by giving the taller state its room up front, and the same answer applies here. It matters less than the others because a macOS dialog is in front at that moment, which is why it was left. ([Notion task](https://app.notion.com/p/3c3719370402815cb958ee571110efcb))
- [ ] **Share the ElevenLabs key field between setup and Settings.** `apiKeyStatusLabel` (`Views.swift`) and setup's badge are the same three cases, string for string and symbol for symbol, and the save path around them — the trimmed submit guard, the `ProgressView` "Checking…" label, the `validateAndSaveAPIKey` task — is duplicated too. A fourth `APIKeyValidity` case, or a reworded badge, currently updates one surface. **Settle the styling question first:** setup deliberately sets type a rung above Settings (`OnboardingType`), so the shared piece has to take its fonts from the caller rather than carry Settings' own. ([Notion task](https://app.notion.com/p/3c371937040281578377f811f00a5492))
- [ ] **Fold the welcome step into `OnboardingPage`.** It re-implements the same scaffold — scroll view, line spacing, column width, page height — at its own margins (32 against `pageMargin`'s 40) and padding (44 against 32), so the single column the layout comment promises is already two. It needs a horizontal alignment and title font to come through as parameters, since it is the one step that is centred. Take it when the welcome step is next edited for another reason; on its own it changes a screen that currently looks right. ([Notion task](https://app.notion.com/p/3c371937040281a9b52fecf01417d3d2))
- [ ] **Follow macOS on what the Accessibility permission is called.** In macOS 27 beta 5 the System Settings pane Scriber sends people to is **Device Control and Data Access**, not **Accessibility**, so every place Scriber says "Accessibility" names something the user cannot find — the recovery pill, onboarding, the Permissions tab, and the README. Wait for macOS 27 stable before changing any of it — a beta name can still move, and the copy has to match what the user actually reads in System Settings rather than paraphrasing it. Scriber supports 26 and 27, which name the same grant differently, so decide then whether one wording can cover both or the text has to branch on the running version. `AXIsProcessTrusted` and the trust-change notification are unaffected: the toggle is picked up within a second in beta 5, most often through the notification rather than the poll.
- [ ] **A zero input volume keeps sending signal for five to seven seconds.** Reproducible again, having been recorded as gone. With the built-in microphone as the Mac's only input, dragging System Settings' input volume to zero leaves Scriber's waveform healthy for five to seven seconds before it flattens, so a short dictation returns nothing and reports nothing wrong. Nudging the slider and returning it to zero flattens it at once, and — the useful part — **connecting any second input device makes it flatten immediately, even when Scriber is still set to the built-in one**. That discriminator is the way in: whatever macOS does when it has one input to choose from, it stops doing with two. A second recipe on the task page makes it disappear just as reliably, and points the same way: the level only lies while nothing else is holding the input open. Establish whether anything in Scriber can see the difference before deciding it is macOS's alone. Do not answer it by restoring the "Microphone cut out" warning — that was removed because Bluetooth earbuds send digital silence between phrases and tripped it constantly, which is still true. ([Notion task](https://app.notion.com/p/3bc719370402805bb391e2b11463adb9))
- [ ] **Survive the input device disappearing mid-dictation.** Disconnecting Bluetooth earbuds while recording freezes the waveform, leaves the timer counting, and loses everything said up to that point — the recording ends in **Transcription failed** rather than returning the audio it already had. Starting or stopping across the same disconnect can also beachball the pill for a couple of seconds, which is a main-thread block the asynchronous start did not cover, so find it with `sample` before changing anything. Decide what the right answer even is first: end the dictation at the disconnect and keep what was captured, or carry on against whatever input macOS falls back to. The truncated failure message is the item above, not this one. ([Notion task](https://app.notion.com/p/3c271937040281cfb561f33bfd6857d1))
- [ ] **Move logic out of the checks that need a human to run them.** All 19 checks under **Inspecting a running Debug build** in `AUTOMATED_CHECKS.md` need computer-use, which cannot reach Scriber from the Claude Code CLI, so none of them run on an ordinary pass. Some are not UI checks at all: the toolbar's dictation count tests one predicate, duplicated at `MainWindow.swift:172` and `updateStatusText` in `Views.swift`, where package tests cannot reach it. Moving it into `ScriberCore` makes it a real test, removes the duplicate, and deletes a doc line. Audit the other 18 the same way. ([Notion task](https://app.notion.com/p/3ba7193704028047a22cd8cd95f310fc))
- [ ] **Find out how ElevenLabs reports a credit top-up.** Whether a top-up raises `character_limit` or lets `character_count` climb past it decides whether anything needs building. If the count climbs past it, the credits display is wrong on a topped-up account: `remainingCredits` is `max(0, totalCredits - usedCredits)` (`ScriberCore/ScribeClient.swift:41`), so the clamp reads an overage as nothing left — an empty bar and 0% sitting directly above a caption saying extended usage is available. The user/subscription endpoint documentation answers it and spends no credit. While there, check the tier label: `subscriptionUsageView` in `Views.swift` renders `usage.tier.capitalized + " plan"`, which prints "Pro_annual plan" for any tier that comes back with an underscore. ([Notion task](https://app.notion.com/p/3b871937040281b5b2cfec28749f8c10))
- [ ] **Fix pasting into the claude.ai prompt box.** It often fails there while typing, ⌘V, image paste, and macOS dictation all work. The box is custom divs with a 0×0 input element parked at the top left of the page, so whatever the engine keys off finds either nothing or the decoy. Add logging that says which branch refused, before changing behaviour — the same engine already handles Raycast's bar and Notes, which have no window at all, so this is a detection gap rather than a missing capability. Read `PASTE_ENGINE.md` first. ([Notion task](https://app.notion.com/p/3be71937040280c39c0dca60629d01b4))
- [ ] **Fix the search-results page that swallows a dictation.** On `x.com/search?q=…` reached by searching from the bar, a dictation started with nothing focused ends silently and inserts nowhere — the engine reports a field it then cannot deliver to, which is the opposite failure to the claude.ai one and the reason both need the same logging before either is changed. Keeping the chosen device selected while it is offline is correct and stays; what has to change is that the reason arrives unreadable. ## v0.10.0

- [ ] **Walk every window with VoiceOver.** Nobody has, so what an assistive user gets is unknown rather than known-good — which is fine for one user and not for a distributed app. Labels exist where someone thought to add them and are absent where nobody did, and the two states are indistinguishable from reading the source: `accessibilityIdentifier` outnumbers `accessibilityLabel` roughly three to one and does nothing for VoiceOver, so a file can grep as full of "accessibility" while announcing badly. Turn VoiceOver on and tab through the main window, Settings' five tabs, onboarding, and every pill phase. Two known shapes to look for: a control whose only content is an SF Symbol announces as its symbol name, and repeated controls in a list announce identically unless each is named for its own row. A code audit cannot replace this — SwiftUI builds no accessibility tree until an assistive client attaches, so neither reading the source nor querying the app from outside without Accessibility permission shows what is actually published.
- [ ] **Redesign the menu bar menu.** Follow the Claude menu reference: lead with Scriber, show the marketing version and build beneath it, and place an Open control on the trailing edge. ([Notion task](https://app.notion.com/p/3ab71937040280298fa7eb2c10a3ff43))
    - Show ElevenLabs credit usage in the menu bar menu. Reuse the existing Usage display in Settings, "cloning" it into the menu bar if possible
    - "Paste/copy last transcription" or "Recent dictation", showing submenu on hover that shows last 3-5 successful transcripts which when clicked will be either copied to clipboard or pasted to the cursor
    - Start a dictation from the menu. `AppCoordinator.startHandsFreeFromMenu` (`AppCoordinator.swift:914`) is written and correct and nothing calls it, so the menu names the shortcut and then offers no way to dictate without it. That matters most to someone whose keyboard cannot press the binding, who has no route at all until they fix it. Put the item above the shortcut hints, and have it read the current phase — it already stops a running recording and reports a busy one.
- [ ] **Overhaul Settings layout.**
    - Search Settings: Type "mic" in the Settings window and land on the setting, whichever of the five tabs holds it. Tabs made Settings scannable; this is for the case where the user knows the setting's name but not which tab owns it. SwiftUI supplies nothing here — it needs an index of every setting with its keywords, a field, results, and a jump that shows which control it landed on. (Update) also consider implementation difficulty now that Settings window is a tabbed interface.
    - Tell the user where the missing permission lives when account access is denied. A key can verify for Speech-to-Text and still be refused account usage, and the tip that covers it (`AppCoordinator.swift:798`) says "Enable User → Read in ElevenLabs to show credits" — it names the permission but not where to set it. Replace that sentence with the path that reaches it: find the key at <https://elevenlabs.io/app/developers/api-keys>, open its three-dot menu, choose Edit, and enable User access under Administration. **Ask Gaf before changing the first sentence** ("This key is scoped for Speech-to-Text but not account usage"), which may stay as it is.
- [ ] **Offer a top pill position** beneath the notch, alongside the current bottom placement. ([Notion task](https://app.notion.com/p/3a671937040280e9869df52acd0c13a7))
- [ ] **Integrate the pill into the MacBook notch.** Treat this as a separate capability from placing the existing pill beneath it.
- [ ] **Name every day group in Dictation history.** Only the day at the top of the list is named, in the titlebar, so every card below it shows no date until scrolled there. Follow Apple Notes: a label above every group, still sticky at the top. ([Notion task](https://app.notion.com/p/3c4719370402814d9539db343590d138))
- [ ] **Accept non-key dictation triggers.** A four- or five-finger trackpad touch and the extra mouse buttons (4, 5, 6) can each start a dictation, alongside key chords. Spokenly does the trackpad one, so treat it as proven rather than exploratory. Build after the single-shortcut pivot lands — every trigger has to report press and release timing, and that contract is what the pivot defines. The task page also proposes double-tapping a modifier, which the pivot rules out for the reason recorded above; whichever ships first decides the other, so do not treat the two pages as one piece of work. ([Notion task](https://app.notion.com/p/3b3719370402804d88cfe80d730c6943))
    - Answer the trackpad's feasibility before designing anything around it, and drop that half outright if either of these does not clear. First, the API. Reading individual trackpad contacts is public only for touches delivered to your own views, and a dictation trigger has to fire while the user is typing in someone else's app; the route known to work globally is the private `MultitouchSupport` framework, undocumented and free to break on any macOS update, on an app that already runs beta releases. Find out what Spokenly's route actually is before deciding this is that. Second, the false trigger: a flat five-finger tap has no built-in binding, but the five-finger *pinch* does — Launchpad, on by default (`TrackpadFiveFingerPinchGesture`) — and a pinch begins as five fingers resting, so Scriber would fire on the way into it. Resting a hand on the trackpad is the same contact set again.
- [ ] **Add the missing space when pasting after a sentence.** When the character before the cursor ends a sentence (`.`, `?`, `!`, and the same followed by a closing quote) with no space after it, insert one before the transcript. Regex detection is enough. `PasteService.textState(of:)` (`PasteService.swift:453`) already reads the focused field's value and selected range for paste-fail detection, so the preceding character is reachable there; fall back to pasting unchanged when the element exposes neither. - [ ] **Let a truncated dictation entry expand in place.** A card's transcript stops at four lines (`DictationHistory.swift:290`) and ends in an ellipsis, so the only way to read the rest is to copy it out — and the cutoff moves with the window, taking more of the transcript as the window narrows. ([Notion task](https://app.notion.com/p/3be7193704028026b3d6ee74888976f5), [earlier design](https://app.notion.com/p/3b871937040280a89e80ea4c7222d2b4))

- [ ] **Offer a Reset to default shortcut button.** Someone who rebinds the shortcut has no way back to what Scriber shipped with, and no way to find out what that was. Put the button beside the recorder in Settings and confirm before it applies, so a curious click costs nothing. ([Notion task](https://app.notion.com/p/3bf7193704028091915fd03840d0d35d))
- [ ] **Say why a secure field refused the dictation.** `PasteService` already refuses to paste into a password box (`PasteService.swift:152`), but it refuses silently after the recording is over and falls through to the clipboard, so the user gets a "Copied" pill and no reason. ## Long-term

- [ ] **Support other providers like Groq** (which also has a generous free tier just like ElevenLabs).
    - Changing the Settings tab name from ElevenLabs to something else. Could be "Providers", "API keys", or something else.
    - Reorganize that tab, now that each provider owns its own API Key and (possibly) Usage section. May need to redesign to ensure good UX and proper visual hierarchy.

    - In anticipation of the upcoming long-form Transcription feature (which may own its own tab in Settings when it arrives), Dictation tab should include an option to select the provider for Dictation—when Transcription lands, it can be configured to use a different provider (yeah I think that's cool).
