# Roadmap

## v0.9.0

The first version anyone can install without Xcode and reach a working dictation on, without being told how. Distribution is proven end to end on a machine that never had Xcode; what setup teaches is not. Nothing ships here that a first-time user on a keyboard Apple did not make cannot get through alone.

- [ ] **Publish the release.** The signed, notarized and stapled disk image is built and verified from a quarantined copy on a clean Mac. What is left is the fast-forward merge, the tag on `main`, and the GitHub release. Follow `RELEASING.md` from step 7.
- [ ] **Publish the Homebrew cask.** `Casks/scriber.rb` is written and its checksum matches the built disk image, but `gafiegarcia/homebrew-tap` does not exist on GitHub, so `brew install --cask gafiegarcia/tap/scriber` cannot resolve. Create the repository and push it in the same release that publishes the DMG it points at. The local tap is a symlink to the working copy; re-tap from the published repository once it is up.
- [ ] **Design what the disk image looks like when it opens.** It is currently unstyled, and `Scriber.app` sits to the right of the `Applications` alias rather than the left, which is backwards for the drag everyone already knows. Put the app on the left, the alias on the right, centre the pair, and add the conventional arrow between them. **Gaf asked what is actually achievable here before anything is built — answer that first**, including whether the arrow can follow the system appearance. ([Notion task](https://app.notion.com/p/3be71937040280a3b838dc5745e842fc))
- [ ] **Find out whether a five-finger trackpad touch can trigger dictation at all.** Gaf's bet is that it beats any key for the trackpad-first majority. Answer feasibility before designing anything around it, and kill it outright if either of these does not clear. First, the API. Spokenly ships four- and five-finger touch, hold and tap alike, and mouse buttons 4 and up, so this is demonstrably achievable and the question is only how. Reading individual trackpad contacts is public only for touches delivered to your own views, and a dictation trigger has to fire while the user is typing in someone else's app; the route known to work globally is the private `MultitouchSupport` framework, undocumented and free to break on any macOS update, on an app that already runs beta releases. Find out what Spokenly's route actually is before deciding this is that. Second, the false trigger: a flat five-finger tap has no built-in binding, but the five-finger *pinch* does — Launchpad, on by default (`TrackpadFiveFingerPinchGesture`) — and a pinch begins as five fingers resting, so Scriber would fire on the way into it. Resting a hand on the trackpad is the same contact set again. This does not replace the keyboard defaults and must not delay the overhaul: a Mac mini driven by a Logitech keyboard and a mouse never touches a trackpad.
- [ ] **Give the menu bar a way to start a dictation.** `AppCoordinator.startHandsFreeFromMenu` (`AppCoordinator.swift:864`) is written and correct and nothing calls it, so the menu names the shortcut and then offers no way to dictate without it. That matters most for the people this milestone is for: someone whose keyboard cannot press the binding has no route at all until they fix the binding. Add the item above the shortcut hints, and have it read the current phase — it already stops a running recording and reports a busy one.
- [ ] **Stop starting a recording on the main thread.** `AudioRecorder.start` wraps `AVCaptureSession.startRunning()` in `queue.sync`, which blocks whoever called it, and the caller is the main thread. Apple documents that call as slow enough to require a background queue, and a Bluetooth headset proves it: opening the microphone forces the headset from music mode into call mode, and the main thread waits out the whole switch — about a second of beachball on every dictation. The global shortcut tap runs on that same main run loop, so every key pressed during the stall queues up behind it. That is survivable only because chord timing reads the hardware timestamp on each event rather than a clock at processing time; go back to reading a clock and a tap becomes a hold again. Making the start asynchronous needs the mode change to survive it: `.releasedAsTap` promotes a recording it expects to already exist, so a release landing before the session is up has to be remembered rather than dropped. `beginOtherAudioMuting` runs on the same thread immediately after and builds a Core Audio tap synchronously, so move both or the stall only halves. No permission prompt is involved in either: the microphone grant is `await`ed and `start` throws rather than asking, and the System Audio grant is requested on a detached task at opt-in time.
- [ ] **Overhaul onboarding.** One scrolling page of stacked cards that teaches one shortcut, never mentions the second mode, and asks for a microphone without ever requiring it to work. Run on a Mac that had never seen Scriber, the verdict was that an app with no onboarding at all would leave someone better off, because they would at least go looking in Settings. Replace the page rather than improving it. Refer to Wispr Flow: one step per page, carefully crafted, nothing on screen that is not the current decision.
    - **Teach hands-free dictation first.** Setup names one shortcut and never mentions the second mode, so a new user learns it exists only by stumbling on it in Settings — and someone whose keyboard has no `fn` cannot reach hands-free at all without editing a binding nobody told them about. The line this replaced named both modes in one breath, badly, which is what made the step cluttered; this wants a step, not a sentence. The single-shortcut pivot collapses it into one lesson, which is the reason to sequence the two together rather than to wait for either.
    - Size the setup window to its content. `fitOnboardingWindow` (`ScriberApp.swift:768`) hands the window the screen's whole height every time it appears, which on a desktop display leaves most of the window empty below the last card. It ignores AppKit's frame for good reason — cascaded under the Dock on a first run, restored too small in a later session — so keep ignoring it and derive the height from the content instead, capped at the screen. Measure the tallest state the page can reach, so the window never grows while someone is reading it.
    - Stop the microphone step's status line jumping. It swaps text and icon together between `waveform` and `waveform.badge.mic` (`Views.swift:1315`), and the badged symbol is the taller of the two, so the row changes height every time the level crosses -60 dB and its text sits off-centre against the icon in one state but not the other. On a noise-cancelling input it fires between every word. Settle the height before touching the wording.
    - Tell people they can opt out of ElevenLabs' **Improve models for everyone**, which is on by default from the moment they make the account setup just told them to create. This is the step that matters most: Gaf ran for months without knowing. The Settings half is a v0.9.1 item; this is the same information where it is first needed.
    - Make the microphone step show a live level. Bring the input up as soon as the permission lands, show the waveform the pill and Sound settings already use, and put the device picker beside it with the built-in microphone marked as recommended. Add a note that input volume is a macOS setting, roughly half being a good place, with a button to it — **the copy naming System Settings → Sound → Output & Input → Input is unsettled and Gaf wants a suggestion.** Half is not a rule of thumb: 50%, three of the slider's six points, is exactly 0 dB, so it holds for a USB microphone as well as the built-in one. The built-in microphone is already chosen on a first run and already reads **(Recommended)** in the picker; carry both into the redesigned step and keep saying nothing about why — Wispr Flow does the same and explains nothing either. The reasons are real but they are ours, not the user's: a Bluetooth headset's microphone drags the headset into call mode, which changes its volume, narrows the audio either side of a dictation, and is the entire reason the mute needs a settle delay. With the same earbuds as output and the built-in microphone as input, none of it happens. Someone in a noisy room, or on a Mac mini with no microphone of its own, still picks their own — the recommendation is a default, never a restriction.
    - End setup with a **Try it** step: a text box, and a line telling the user to click it and press the shortcut they just chose. A wrong input volume shows up here, one step from the page that fixes it, and everyone else gets a first dictation that works.
    - Give **Mute other audio while recording** a step of its own. The toggle sits among the trailing options today, where a first-time user meets it as an afterthought rather than a decision. Ask it as a step, in the same shape as the permissions above it, and carry a tip for headphone users: with a Bluetooth speaker or earphones, audio resuming after a dictation can stay in call-mode quality for a second or two before it returns to normal. Build it after the System Audio Recording row above: that row decides what Scriber can say about the grant at all, and today `requestOtherAudioAccess` only logs the answer, so nothing can report it.
    - Give System Audio Recording a signpost row on the Permissions tab, with an **Open Privacy & Security** button and no claimed status. It cannot report status the way the others do: `AVCaptureDevice.authorizationStatus` covers the microphone and `AXIsProcessTrusted` covers Accessibility, but Core Audio ships no preflight for process taps — the only way to read the state is to attempt a tap, which is what raises the prompt. A status derived from the last mute attempt would be blank or stale far more often than right: a failed mute *start* is deliberately silent (`AppCoordinator.swift:1542`), and `otherAudioMuteStatus` is only set when a *restore* fails. The row says what macOS will not report and points at where to look. It must not duplicate the Sound tab's existing link button (`Views.swift:882`), which stays beside the toggle it explains.
    - Make onboarding's meter read like the pill's. Both already draw the same `AudioLevelWaveform` at the same cadence, so what separates them is presentation: the pill gives it 58×24 pt in red over its own material, onboarding stretches it to 42 pt tall and full width in the accent colour over a `.quaternary` panel. A bar never falls below 2 pt, so the taller the frame the more a real but quiet signal collapses into the same flat line as no signal at all — the distinction the step exists to show. Match the pill's proportions and contrast rather than inventing a second meter; that rendering is the one legible enough to catch a stream going silent mid-recording.
    - Leave one meter behind, not two. Sharing the view was not enough to stop the divergence above, because each call site still chose its own frame, colour and backing. Give `AudioLevelWaveform` named presentations to pick from rather than raw numbers, and make its 2 pt bar floor proportional to the frame instead of fixed, so a quiet signal reads as quiet at any size and a third call site cannot reintroduce this by choosing a taller box. It also lives inside `PillController.swift`, which is what makes every other use look like a borrowing; a view two features depend on belongs in its own file.
    - Make the microphone step prove itself rather than offer itself. `OnboardingView` already runs a live meter and flips a label to "Audio signal detected" (`Views.swift:1315`), but nothing requires the user to speak into it, so setup completes with the microphone never once tested. Gate the step on signal actually observed, and watch for long enough to survive the item below: a zero input volume can read healthy for five to seven seconds before it flattens, which is longer than anyone looks at a meter.

## v0.9.1

- [ ] **Follow macOS on what the Accessibility permission is called.** In macOS 27 beta 5 the System Settings pane Scriber sends people to is **Device Control and Data Access**, not **Accessibility**, so every place Scriber says "Accessibility" names something the user cannot find — the recovery pill, onboarding, the Permissions tab, and the README. Wait for macOS 27 stable before changing any of it — a beta name can still move, and the copy has to match what the user actually reads in System Settings rather than paraphrasing it. Scriber supports 26 and 27, which name the same grant differently, so decide then whether one wording can cover both or the text has to branch on the running version. `AXIsProcessTrusted` and the trust-change notification are unaffected: the toggle is picked up within a second in beta 5, most often through the notification rather than the poll.
- [ ] **A zero input volume keeps sending signal for five to seven seconds.** Reproducible again, having been recorded as gone. With the built-in microphone as the Mac's only input, dragging System Settings' input volume to zero leaves Scriber's waveform healthy for five to seven seconds before it flattens, so a short dictation returns nothing and reports nothing wrong. Nudging the slider and returning it to zero flattens it at once, and — the useful part — **connecting any second input device makes it flatten immediately, even when Scriber is still set to the built-in one**. That discriminator is the way in: whatever macOS does when it has one input to choose from, it stops doing with two.
