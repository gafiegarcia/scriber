# Paste Engine

This is the current decision record for delivering a finished dictation into another macOS app. It records the invariants, not the investigation history that produced them.

## Target rule

Delivery follows the text cursor that has keyboard focus when transcription finishes. It does not retain the app, element, or selection that was focused when recording began. Record start therefore performs no Accessibility lookup; it may query the window server only to decide which screen should hold the pill.

At delivery time, the frontmost process is the normal paste target. Keyboard focus may instead belong to a different process presenting a nonactivating panel, as Raycast does. Redirect to that process only when its focused Accessibility ancestry genuinely exposes text input. Never redirect delivery into Scriber itself.

Accessibility is consulted for one purpose beyond that redirect: refusing a positively identified secure text field. Dictation must never be pasted into a password box. Nothing else about the focused element is read, and nothing about it can confirm a delivery — see below.

Accessibility requests are synchronous cross-process calls, so each message has a 0.2-second timeout and traversal is bounded.

## The delivery, end to end

This is the whole method. One way of inserting, one way of confirming, no fallbacks.

1. Resolve the target process: the frontmost application, or whoever holds keyboard focus when the two disagree. Refuse outright if a secure text field has the cursor.
2. Snapshot the general pasteboard, clear it, and publish the transcript lazily as `.string` on an item marked with all four compatibility types:

   - `org.nspasteboard.TransientType`
   - `org.nspasteboard.ConcealedType`
   - `org.nspasteboard.AutoGeneratedType`
   - `de.petermaurer.TransientPasteboardType`
3. Post a Command-V to that process.
4. Dismiss the pill immediately, before anything is known. Confirmation takes up to a second and the user should not have to watch it.
5. Wait up to one second for the destination to request the promised string. That request is the confirmation, and the only thing waited on.
6. If it arrives, the delivery landed. Restore the snapshot **half a second later** — never immediately. See below.
7. If it never arrives, nothing was inserted. Replace the concealed item with the transcript as ordinary text and show the copied-result recovery message.

### Why the restore waits

A destination may read the pasteboard twice: once to see what is on offer, and again to insert what it saw. Restoring between those two reads hands it the clipboard the user had before, which it then pastes instead of the dictation.

This produced two bugs that looked unrelated for an entire session. Google Docs pasted the previous text into a table cell about one attempt in five. Raycast Notes, on a freshly opened note, pasted nothing at all — because the previous clipboard item was an image, which it cannot accept — and looked for all the world like a broken delivery method. Two costumes, one cause.

`restoreIfUnchanged` keeps the delay safe: anything else writing to the clipboard moves the change count and the restore is abandoned rather than overwriting it.

## Confirmation

**The destination requesting the concealed item is the only evidence, and it is sufficient.**

The transcript is published only as a lazily promised string, so it does not exist until something asks for it. A destination that never asked cannot have inserted it, and a destination that asked was pasting.

Nothing observed after the paste is admitted. Accessibility state is not a record of what a paste did: a focused field disappearing reads identically to text arriving, a live page rewrites itself on its own timers, and during a hands-free dictation the user may type into the box themselves. Each of those was read as a successful delivery at some point.

What is focused *before* the paste is not evidence either. It says where a paste would land, never that one did. A real `AXSearchField` held the cursor through three consecutive Calendar deliveries that inserted nothing.

There are two outcomes, not three. A dictation lands, or it does not and the recovery pill says so. Scriber never reports that it is unsure.

## Command-V, and only Command-V

The event source is private rather than the combined session state. A modifier still held when delivery fires — a hands-free chord not yet released, or a launcher hotkey — merges into a session-state event and turns the paste into Shift-Command-V or Option-Command-V.

Pressing the destination's own Edit ▸ Paste item through Accessibility is not a fallback and must not be reintroduced. Opening a menu takes keyboard focus off the field being pasted into, so the Paste it then performs has nowhere to go. It also blocks the main thread on an app that is still starting, and it makes a failed delivery produce two alert sounds where one is correct.

Posting the event at the HID level rather than into the target process is also refuted. It fixed nothing and made Google Docs paste the previous clipboard item.

Writing the transcript straight into the focused element through Accessibility is not a second delivery route. Almost nothing accepts it — Ghostty publishes an `AXTextArea` of 13,766 characters and refuses, and an Electron app publishes nine nested groups and nothing writable — and where an element does report `AXSelectedText` as settable, setting it can return `.success` and change nothing. It would need its own confirmation layer to fix no known failure.

Raycast and Spotlight have no menu bar at all, so Command-V is the only route that can reach them.

## Diagnostics

`PasteService` writes privacy-safe lines per delivery at `notice` level under subsystem `com.gafiegarcia.scriber`, category `paste-target`. Process identities, focused role and subrole, `asked`, and `elapsedMs`. Never transcript text.

```bash
/usr/bin/log show --last 30m --predicate 'subsystem == "com.gafiegarcia.scriber" AND category == "paste-target"' --style compact
```

`asked=0` means the delivery did not happen — not that it might not have. Capture this first for a new delivery complaint, before forming a hypothesis.

The level matters: macOS does not persist `info`, so a diagnostic written at that level cannot be read back and the engine is debugged blind.

## Regression baseline

Destination-by-destination expectations live in [`MANUAL_CHECKS.md`](MANUAL_CHECKS.md). Also verify that moving focus during transcription delivers to the final cursor.

One destination once appeared to break the confirmation rule: Raycast Notes on a freshly opened note asked for the transcript and inserted nothing. It was asking honestly, and its paste was handed the user's previous clipboard by a restore that ran too early. The rule has no known exception.

Two consequences of it are accepted rather than fixed. A web page runs its own paste handler and reads the clipboard whether or not anything was focused, so a page with no cursor reports a successful delivery. Finder with nothing focused pastes a `.textClipping` file and reports success, which is what a paste with no text target means to Finder. Both match what other dictation apps do, and both cost nothing: the user pressed dictate with no cursor.

## The character count is for detection, not for belief

An element qualifies as text input when it exposes a character count, which is how a custom control with no editable role is recognised at all. That is used to decide whether keyboard focus should redirect delivery to a nonactivating panel, and for nothing else. It was once also used to conclude a cursor was present, which it cannot: a page presents an `AXGroup` reporting zero characters, no editable role and no settable selection after a text field is clicked and then left.

## Rejected changes

- Do not put Accessibility traversal back on record start.
- Do not select the target from the frontmost application alone.
- Do not press the destination's Paste menu item. See above.
- Do not treat a dispatched Paste command as insertion. `AXUIElementPerformAction` answers `.success` on a menu item that does nothing.
- Do not accept anything but the concealed-item request as confirmation — not observed Accessibility mutation, not what was focused beforehand, not an ordinary clipboard-manager-visible string request.
- Do not add a third outcome for deliveries Scriber cannot judge. There are none.
- Do not select, copy, replace, or undo destination text to verify insertion; it risks corrupting user state.
- Do not add per-app exceptions from an anecdote. Capture the log first.
